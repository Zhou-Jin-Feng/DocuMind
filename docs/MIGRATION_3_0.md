# 迁移到 DocuMind 3.0.0

3.0.0 统一当前 Web 入口和文件路径行为。它不是对旧 Gradio 启动方式的兼容补丁；升级前需核对配置、数据位置和调用方版本限制。

## 兼容性矩阵

| 项目 | 旧版行为 | 3.0.0 行为 |
|---|---|---|
| Web 入口 | 可使用 Gradio 启动脚本 | React 工作台 + `python -m app.api` |
| 旧服务参数 | `SERVER_HOST`、`SERVER_PORT`、`SHARE_GRADIO` | 不再使用；API采用 `API_HOST`、`API_PORT` |
| 默认 `.env` | 相对终端工作目录 | 从包含 `app/` 的项目根加载 |
| 应用相对运行路径 | 可能随当前工作目录变化 | 相对项目根；绝对路径继续有效 |
| 注册表 / 上传 / 日志 | 既有数据文件 | 不自动移动或改写；先明确配置真实路径 |
| 评测报告默认位置 | 部分工具写入 `evaluation/reports` | 新报告写入 `artifacts/evaluation`，DS-06写入其子目录 |
| 显式CLI文件参数 | 调用者指定位置 | 保持原义；相对输入/输出仍依调用者目录解释 |
| 纯检索契约 | Schema `1.0`、`dense-v1` | 不变；`service_version`更新为`3.0.0` |

## 升级前

1. 在独立位置备份原配置、Registry、上传文件及对应向量存储；备份范围应按实际部署确认。
2. 记录原来的工作目录和路径值。若依赖旧cwd，先将重要路径转换为指向现有数据的绝对路径，再切换源码。
3. 不直接覆盖已有 `.env`。对照当前 `.env.example` 去掉旧 Gradio 参数，填写 API 和依赖地址。
4. 核对 Consumer 是否将 `service_version` 严格限制为2.x。Schema不变不等于所有调用方版本钉选会自动接受新应用版本。
5. 先以独立测试数据验证启动、ready、上传、检索与问答，不在正式数据目录中试验升级/恢复。

## 启动与路径

当前入口见[运行说明](DEMO_SCRIPT.md)。应用初始化会创建已配置的数据/日志父目录，但不会替你迁移旧文件。若发现空知识库，应先检查Registry、上传根和Milvus的配置是否指向原数据，不要立即删除或重建。

Docker继续使用Compose中指定的持久卷路径。检查实际 `.env` 和Compose覆盖项，不要把示例中的重启策略、端口或卷名称当作当前环境的唯一配置。升级时不要使用 `docker compose down -v` 清空现有数据。

## 旧架构与回退

需要Chroma/Gradio时使用对应的 `v1.7.1` 标签及其依赖环境。Chroma与Milvus数据不是可直接互换的目录，不能通过切换代码就认为存储已经迁移。

回退应恢复匹配的源码、配置与经过验证的备份，先确认数据/接口兼容再恢复业务调用。本文不提供自动改写Registry或向量库的迁移脚本，也不保证任意跨版本回退可原地完成。

## 验证与发布边界

普通确定性测试不等于真实服务验证。发布候选需完成相应环境的依赖安装、真实Milvus隔离集成、前后端回归、镜像构建与接口检查；历史实验数据和报告保持原始版本/输入身份，不因升级应用版本而改写。

源码标识为3.0.0不代表对应tag或GitHub Release已创建。实际发布节点以仓库引用和发布页为准。检索请求/响应字段、错误语义和资源控制见[纯检索API](RETRIEVE_API.md)。
